# 药小伴领域规则与业务决策表

本文是 beta.5 的产品经理 / 工程共同约定。页面文案、客户端领域函数、云函数校验和测试应以这些规则为准；如果某个页面需要另一种解释，应先修改规则和测试，再修改 UI。文中的“记录”都表示用户主动填写或确认的私人记录，不代表系统观察到真实服用行为。

## 1. 产品边界

| 问题             | beta.5 的决定                                  | 用户能看到的结果                                   |
| ---------------- | ---------------------------------------------- | -------------------------------------------------- |
| 药名来自哪里     | 只保存用户输入；已有药名只能作为轻量建议       | 不自动补全说明书、适应症、剂量或推荐               |
| 用量是否正确     | 应用不判断                                     | 表单提示“按医嘱或说明书填写”                       |
| 服用是否真实发生 | 只有用户点击“已服 / 未服 / 额外使用”才形成记录 | 文案使用“记录、预计、提醒”，不使用“已验证服药”     |
| 多人关系         | 一个微信账号内的本人 / 家庭成员代管档案        | 不是跨账号共享药箱，不提供协作邀请                 |
| 照片识别         | 只保存用户选择的药盒照片，不做 OCR / AI 识别   | 照片仅用于在药箱里快速辨认                         |
| 系统日历         | 用户主动授权后请求写入                         | 只能说明“曾请求写入”；不能查询、修改或删除系统事件 |

## 2. 有效期与管理期限

### 2.1 决策表

| 包装标注              | 开封信息                     | 管理期限     | 说明                                         |
| --------------------- | ---------------------------- | ------------ | -------------------------------------------- |
| 完整日期 `YYYY-MM-DD` | 无                           | 包装日期     | 到期当天仍有效，下一天起显示已到期           |
| 月份 `YYYY-MM`        | 无                           | 当月最后一天 | 保留月份精度，不把月末伪装成用户填写的日精度 |
| 完整日期 / 月份       | 开封日 + 开封后天数          | 两者较早者   | 同时展示包装标注和管理期限，明确来源         |
| 任意日期              | 开封后天数无效、缺失或未成对 | 不接受该组合 | 要求开启日期和天数完整成对填写               |
| 任意有效包装日期      | 开封日在今天之后             | 不接受       | 不允许记录尚未发生的开封                     |
| 任意有效包装日期      | 开封日在包装有效期之后       | 不接受       | 日期关系不可信，要求重新核对                 |

### 2.2 计算公式

```text
packageExpiry = 完整日期
              或 YYYY-MM 对应月份的最后一天

openedExpiry = openedDate + (afterOpenDays - 1) 天
effectiveExpiry = min(packageExpiry, openedExpiry)
```

开封当天计为第 1 天，所以“开封后 1 天”管理到开封日；“开封后 7 天”管理到开封日后第 6 个日历日。所有业务日期按 `Asia/Shanghai` 解释，不依赖运行机器所在时区。

### 2.3 风险显示

- `today < effectiveExpiry`：有效；如果剩余天数不超过设置阈值，显示即将到期。
- `today = effectiveExpiry`：仍有效，但显示“今天到期”风险。
- `today > effectiveExpiry`：已超过管理期限，显示需要处理；不再把原计划作为普通可服任务继续引导。
- 只有包装日期、没有可靠开封期限时，不推断开封后的日期。

## 3. 三种使用方式

| 使用方式               | 是否需要计划                         | 今天页                          | 库存预测                                  |
| ---------------------- | ------------------------------------ | ------------------------------- | ----------------------------------------- |
| 只管效期 `expiry_only` | 否，必须为空                         | 不生成固定服药任务              | 可显示用户盘点，但不生成计划消耗 / 用完日 |
| 固定服用 `scheduled`   | 是，每天或指定星期 + 时间 + 每次用量 | 展开今日任务，可记录已服 / 未服 | 依据固定计划和记录估算                    |
| 按需使用 `as_needed`   | 不生成固定时间计划                   | 不生成固定服药任务              | 不虚构预计用完日；额外使用仍可由用户记录  |

固定计划的开始日、可选结束日都必须不晚于管理期限。页面最多提供 6 个提醒时间；服务端兼容 schema 可接受更多历史数据，但当前 UI 不主动创建超过 6 个时间。

## 4. 计划版本与任务

计划不是覆盖式设置，而是版本化记录。保存新计划时：

1. 新计划获得新的 ID、版本 / revision 和 `effectiveFrom`；
2. 药盒的 `activePlanId` 指向新计划；
3. 旧计划写入 `effectiveTo` / `supersededAt`，保留供历史解释；
4. 旧计划对应的日历台账标记为待处理，不能继续当作当前计划；
5. 旧日期的服用记录不被新计划改写。

一个固定任务由 `planId + 本地日期 + 时间` 组成稳定 occurrence key。计划展开满足：

```text
计划开始日 <= 本地任务日 <= 计划结束日（若有）
effectiveFrom <= 任务时间 < effectiveTo（若有）
```

指定星期只在选中的星期生成；按需计划永远不展开成固定 occurrence。计划服用记录默认只允许在任务到达前 10 分钟内确认，不能提前很久代记未来任务。

## 5. 预计余量

### 5.1 基线和计算

最近一次用户确认的库存盘点是唯一实际基线。计算从该盘点时间之后开始，且在药盒管理期限处停止：

```text
预计余量 = max(0,
  最近盘点数量
  - 已发生的固定计划剂量
  - 有效的额外使用数量
  + 被标记未服的对应计划剂量
  + 盘点之后用户确认但不属于当前自动展开槽位的已服数量调整
)
```

同一 occurrence 已记录“已服”时，不会在计划消耗之外再扣一次；撤销该记录会恢复未记录时的计划语义。重新盘点不删除旧盘点或服用历史，只从最新盘点建立新的计算起点。

### 5.2 不确定性优先

| 情况             | 数量显示             | 用完日                   |
| ---------------- | -------------------- | ------------------------ |
| 没有盘点         | 未记录 / 尚未盘点    | 不预测                   |
| 没有固定计划     | 盘点数量可显示       | 不预测                   |
| 按需使用         | 盘点数量可显示       | 不预测                   |
| 单位不一致       | 不做跨单位计算       | 不预测并提示核对单位     |
| 计划已结束       | 按已发生计划算到当前 | 不把已结束计划延伸到未来 |
| 预计消耗超过盘点 | 最低显示 0           | 单独显示首次不足时间     |
| 计划跨过管理期限 | 计算截止管理期限     | 不在到期后继续预测       |

库存单位（片、粒、毫升等）不自动换算。剂量、盘点、额外使用必须使用同一单位；保存库存时必须明确选择单位。

## 6. 服用记录和撤销

| 操作         | 记录状态        | 对预计库存的影响                                              | 可否撤销         |
| ------------ | --------------- | ------------------------------------------------------------- | ---------------- |
| 点击已服     | `taken`         | 对应计划消耗不重复扣；若是提前 / 计划外确认，则按实际数量调整 | 可以             |
| 点击未服     | `skipped`       | 返还对应计划槽位的自动消耗                                    | 可以             |
| 记录额外使用 | `extra`         | 按用户输入数量单独扣减                                        | 可以             |
| 撤销         | `undoneAt` 非空 | 该条记录不再参与计算，回到无该记录的语义                      | 幂等，不重复撤销 |

同一固定任务的记录以计划 ID 和任务时间稳定定位；重复点击不会产生第二条有效记录。网络重试使用 requestId / occurrence key 幂等。历史记录只代表记录事件，不会因药盒归档或计划修改而消失。

## 7. 药盒状态与生命周期

| 状态       | 是否出现在今天 / 药箱活动列表 | 是否生成计划 / 提醒          | 操作                         |
| ---------- | ----------------------------- | ---------------------------- | ---------------------------- |
| `active`   | 是                            | 是，受管理期限和计划规则约束 | 编辑、盘点、记录、归档、删除 |
| `archived` | 否，进入已归档区              | 否                           | 恢复或永久删除               |
| `deleting` | 不可读 / 不可继续写业务       | 停止                         | 删除重试直到级联清理完成     |

归档前会停止活动计划、取消待发提醒并标记日历台账 stale；恢复只恢复管理列表，不自动重启旧计划。永久删除按药盒 ID 级联清除计划、盘点、服用记录、提醒任务、日历台账、照片媒体和药盒本身。删除中的记录不能被普通编辑覆盖；版本冲突要求刷新后重试。

## 8. 照片生命周期

照片是可选展示附件，不影响只记录药名和有效期的最短流程。

```text
选择相机 / 相册
  → 客户端压缩并检查不超过 2 MiB
  → prepare：服务端发 24 小时、账号绑定的媒体票据
  → wx.cloud.uploadFile（正式云）或本地保存（隔离演示）
  → commit：校验完整路径、大小、格式和尺寸
  → 绑定到药盒；药箱卡片显示缩略图
```

服务端只接受完整的 JPG / PNG / WebP；单边不超过 6000px，总像素不超过 20 MP。更换、移除、上传失败、保存冲突、药盒永久删除和账号删除都要触发清理。清理失败保留 `cleanup_pending` 供重试，不能向用户声称对象已经删除。导出文本不携带图片文件或任何内部路径。

## 9. 系统日历

- 只有用户主动点击写入并授权后才请求系统日历权限。
- 从“上海今天”和计划开始日中较晚者起算，最多写入 90 天，并在管理期限前截止。
- 每个计划槽位按计划、日期、星期、时间等稳定字段生成 fingerprint；标题隐私偏好和滚动窗口不改变槽位身份。
- 多事件逐条写入并逐条记录成功结果；部分失败返回 partial，重试只补未成功事件。
- 计划、药名、有效期或隐私标题变化会将旧台账标为 stale，页面提示用户去系统日历手动删除旧事件。
- 小程序不能查询事件是否仍存在，也不能修改 / 删除事件；数据库台账只表示“曾经成功请求写入”。

## 10. 隐私同意与数据删除

- 当前隐私版本未同意前，任何健康相关写操作都被阻止。
- 照片属于用户主动选择的可选附件；申请相机或相册只发生在用户点击照片入口后。
- 正式云端按账号所有权访问；客户端数据库权限关闭，不能依赖客户端规则代替云函数校验。
- 导出为用户可携带的 JSON；照片文件和内部地址不放进文本导出。
- 账号删除采用幂等墓碑和可重试清理；业务数据立即对用户不可访问，活动数据按约定 SLA 清理。
- 手机系统日历是外部系统，账号删除不能自动清除其中已写入的旧事件，必须明确提示用户自行清理。
